# Contributing to Rewind

Thanks for helping. This guide covers setup, how the app is put together, the conventions the
code follows, and how changes get verified and released.

## Setup

1. Install [Bun](https://bun.sh) 1.3+ (the only supported package manager — don't use npm or
   yarn), plus Android Studio (JDK 21, Android SDK) and/or Xcode.
2. `bun install`. This also applies `patches/` to dependencies (Bun's built-in patching).
3. `bun run android` (or `bun run ios`) builds a development build and installs it.
4. `bun start` runs Metro for that build. `bun run start:mock` seeds mock data.

The native projects (`android/`, `ios/`) are generated by `expo prebuild` and are not committed.
Change native configuration through `app.json`, config plugins, `modules/` or `patches/`, never
by editing the generated folders.

## Project layout

| Path | Contents |
|---|---|
| `app/` | expo-router screens: `(tabs)/` home, camera, profile; `album/[id]`, `album/timelapse`, `album/compare`, `album/settings`, `onboarding` |
| `components/` | UI by domain: `camera/`, `timelapse/`, `timeline/`, `face/`, `profile/`, `ui/` |
| `context/AppContext.tsx` | The single source of truth for photos, profile, settings and albums |
| `hooks/` | Feature logic (face-scan and q95 backfills, timelapse, auto-capture, streaks, …) |
| `utils/` | Pure helpers: face metrics and trend, alignment, playback, storage, import/export, … |
| `modules/face-mesh/` | Expo native module wrapping MediaPipe Face Landmarker (Kotlin + Swift) |
| `patches/` | Dependency patches (see "Native code") |
| `constants/theme.ts` | Design tokens |
| `__tests__/` | Jest tests, mirroring the source layout; shared mocks in `__tests__/helpers/` |

## How the main pieces work

- **Data.** `AppContext` loads everything from AsyncStorage on launch. Mutations update React
  state, then save through a serial queue; `updatePhotos` resolves with whether its save reached
  storage. Read and write app data through `AppContext`, not `utils/storage`.
- **Photos** are files in the app's document directory, stored as q95 JPEGs. A background pass
  (`usePhotoEncodeBackfill`, on the album screen) re-encodes any photo that isn't yet, deleting
  an original only after the entry pointing at its replacement is saved.
- **Face scans.** `utils/faceScan.ts` runs MediaPipe on an upright 1024 px copy of each photo
  and stores eye positions (for timelapse alignment) and about ten measurements (for the face
  trend) on the photo. `useFaceScanBackfill` scans photos that need it. Bump
  `FACE_SCAN_VERSION` to rescan everything after changing what a scan stores.
- **Face trend.** `utils/faceMetrics.ts` turns a 478-point mesh into measurements;
  `utils/faceTrend.ts` corrects them for camera distance and pitch and smooths them into a
  trend. Both are pure and fully unit-tested.
- **Camera.** VisionCamera with an MLKit frame processor drives the live face guide.
  `utils/cameraPreview.ts` maps detector coordinates onto the (mirrored, cropped) preview.
  Results arrive from the frame processor as read-only arrays: map them into new arrays.
- **Timelapse.** `TimelapsePlayer` keeps a window of decoded frames around the playhead and
  switches frames on the UI thread (`useFrameCallback`); `utils/playback.ts` holds the timing
  maths.

## Conventions

- TypeScript everywhere; import through the `@/` alias (`@/utils/storage`).
- Use the design tokens in `constants/theme.ts` (`Colors`, `Fonts`, `Spacing`, …) and the mono
  font; don't hardcode colors or font families.
- Haptics go through `@/utils/haptics`, never `expo-haptics` directly.
- Storage reads guard `JSON.parse` and fall back to defaults on corrupt data.
- Comments explain *why* (a measured number, a platform quirk), not what the code does.
- Commits follow [Conventional Commits](https://www.conventionalcommits.org):
  `type(scope): description`, with types `feat`, `fix`, `perf`, `refactor`, `docs`, `test`,
  `build`, `ci`, `chore`, `style`.

## Tests and checks

Run these before opening a pull request; CI runs the same:

```bash
bun run typecheck
bun run lint
bun run test
bunx expo-doctor
```

- Write the test first when fixing a bug: it should fail for the reason the bug exists.
- Component tests use React Native Testing Library. `__tests__/helpers/reanimatedMock.tsx`
  models Reanimated (including asynchronous JS→UI writes) and `fileSystemMock.ts` stands in for
  expo-file-system.
- Anything performance-related needs a measurement on a real device in a **release** build
  (`./gradlew :app:assembleRelease` in the generated `android/`). Debug builds run JS in
  development mode and aren't representative.

## Native code

- **`modules/face-mesh`** is a local Expo module, autolinked from `modules/`. It bundles the
  `face_landmarker.task` model; Android uses `com.google.mediapipe:tasks-vision`, iOS the
  `MediaPipeTasksVision` pod. The JS wrapper returns `isFaceMeshAvailable() === false` when the
  module isn't in the build, and the face features hide.
- **`patches/react-native-vision-camera@4.7.3.patch`** stops VisionCamera adding a video output
  whenever a frame processor is attached; that forced GL stream sharing and a visibly softer
  preview. To change a patch: `bun patch react-native-vision-camera`, edit the package in
  `node_modules`, then `bun patch --commit node_modules/react-native-vision-camera`.

## Dependencies

App dependencies are pinned by the Expo SDK. Upgrade them with `bunx expo install --fix` (CI's
`expo-doctor` fails when they drift) and run a clean install if doctor reports duplicates.
Dependabot only updates GitHub Actions.

## CI/CD

| Workflow | When | What |
|---|---|---|
| `ci` | every push to `main` and pull request | typecheck, lint, tests with coverage, expo-doctor, Metro bundle for both platforms |
| `android` | changes to dependencies, `app.json`, `modules/` or `patches/` (or run by hand) | full native debug build |
| `eas-update` | after `ci` passes on `main` | publishes an over-the-air update to the `preview` branch |
| `eas-build` | version tags `v*` (production), or by hand | EAS cloud builds |
| `release` | version tags `v*` | GitHub Release with generated notes |

Third-party actions are pinned to a commit SHA with the version in a trailing comment;
GitHub's own `actions/*` use major tags. Dependabot updates both. `gradle/actions` stays on v5
because v6 puts its caching under Gradle's Terms of Use.

The EAS workflows need a one-time setup and skip themselves until it's done:

1. `bunx eas-cli init` to link the project (fills in the project id and updates URL in
   `app.json`), then commit the change.
2. Create an access token at expo.dev → Account settings → Access tokens, and add it as the
   repository secret `EXPO_TOKEN`.

To release: bump `version` in `app.json`, commit, then `git tag vX.Y.Z && git push origin vX.Y.Z`.

## Pull requests

- Keep each PR focused, with a description of what changed and why, and how you verified it
  (tests, and device screenshots or recordings for UI and performance changes).
- New behavior comes with tests; bug fixes come with a test that reproduces the bug.
- Be kind — see the [Code of Conduct](CODE_OF_CONDUCT.md).
